Trust

Security

This page describes two different things: how this website is secured today, and the security bar our products must clear before anyone can use them.

Last updated 27 October 2026

We make no claim to hold any security certification. Where this page describes controls for BreatheFree, it describes release requirements that have not yet been met — not controls that are in place today.

This website

The site is deliberately boring, because boring is the most reliable security property available to a marketing site.

  • Static output. Every page is pre-rendered HTML. There is no application server, no database and no session to steal. The only server-side code is the two small handlers behind the beta early access: one accepts nothing but its form, the other nothing but the confirmation link we email. They check every field against a fixed list or length and write to a file outside the public site.
  • No third-party code. The site loads no external scripts, fonts, images or stylesheets. A supply-chain compromise of an analytics or font vendor cannot reach visitors of this site, because there is no such vendor in the page.
  • No accounts, no cookies. There is nothing to log in to and no session state, so there are no credentials here to lose.
  • Minimal data. The early-access and contact forms compose a message in your own email client rather than posting to a server we run. We hold what you chose to send, and nothing else. The beta early access form is the exception: it is sent to our web server and asks only for what an invite needs, as the privacy notice describes.

What BreatheFree must satisfy before release

BreatheFree handles information people would not want disclosed. It is not released, and it will not be released until the following are in place and independently checked:

  • Data-flow mapping, threat modelling and a privacy impact assessment completed.
  • Authentication built on OAuth/OIDC with short-lived tokens and secure device storage.
  • Protected data encrypted in transit and at rest.
  • Consent versioning, purpose limitation and revocation enforced on the server, not merely reflected in the interface.
  • Verified export and deletion, with completion that can be audited rather than assumed.
  • Sensitive notification text off by default, so a lock screen never discloses someone's health status.
  • Crash reporting and diagnostics that carry no health-entry payloads.
  • Abuse prevention, rate limiting, monitoring and a written incident-response procedure.
  • Independent penetration testing of the mobile application, the API and the cloud environment.

These are release gates. If one is not met, the release does not happen.

Reporting a vulnerability

If you believe you have found a security issue in this website or in anything else we run, please tell us at security@tetherhealthgroup.com. The same contact is published in our security.txt.

Please include, as far as you can:

  • What the issue is and where you found it.
  • Steps that reproduce it.
  • What an attacker could achieve with it.

We will acknowledge your report, keep you informed while we investigate, and credit you if you would like to be credited. Please give us a reasonable opportunity to fix an issue before disclosing it publicly, and please do not access or modify anyone else's data, degrade our service, or run automated scanning that would.

We do not currently run a paid bug-bounty programme. We are grateful anyway.
